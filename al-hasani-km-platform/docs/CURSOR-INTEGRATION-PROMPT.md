[الاستراتيجية 1 — الموصى بها: هوية مشتركة + قاعدة بيانات منصّة منفصلة] (أقصى عزل، صفر مخاطرة على (ب))

== ضوابط الأمان الإلزامية (طبّقها حرفياً) ==
1) نسخة احتياطية أولاً: تأكّد من وجود نسخة احتياطية حديثة لقاعدة بيانات (ب) قبل أي أمر. لا تتابع بدونها.
2) لا تلمس مستودع/قاعدة/إعدادات (ب) إطلاقاً. اعمل داخل مشروع (أ) فقط، وعلى فرع git مستقل.
3) Prisma لا يدير جداول (ب) أبداً. قبل أي migrate، استخرج الـ SQL وراجعه يدوياً وتأكّد أنه يمسّ جداول المنصّة فقط:
   استخدم  npx prisma migrate diff  أو  prisma migrate deploy  على قاعدة المنصّة المنفصلة. لا تستخدم prisma db pull
   على قاعدة (ب)، ولا تشغّل أي migrate وDATABASE_URL يشير إلى قاعدة (ب).
4) user_profiles للقراءة فقط: المنصّة تقرأ صفّ المستخدم لتحديد الدور ولا تكتب فيه إطلاقاً. (دور المتعلّم محفوظ في
   user_metadata.km_role ويُطابَق في جدول User الخاص بالمنصّة عبر ensureKmUser — مُنفَّذ مسبقاً).
5) RLS وسياسات (ب): لا تعدّل أي سياسة قائمة. أضِف فقط ما يخصّ المنصّة في نطاقها/قاعدتها.
6) التخزين: أنشئ دلاءً جديدة فقط (academy-videos). لا تمسّ دلاء النظام أو سياساتها.
7) Gemini: أعِد استخدام المفتاح للقراءة (التضمين) فقط. لا تغيّر أي إعداد Gemini في (ب).
8) اختبار دخان بعد كل خطوة: تأكّد أن دخول نظام (ب) وعملياته الأساسية تعمل كما هي. عند أي شكّ — تراجع وأبلغني.

== ما هو مُنفَّذ في كود المنصّة (للفهم) ==
- مزوّد مصادقة عبر AUTH_PROVIDER=supabase|local. عملاء Supabase في src/lib/supabase/* وخرائط الأدوار في roleMap.ts.
- src/lib/auth.ts:getSession() يقرأ جلسة Supabase + user_profiles (قراءة) ويبني SessionUser.
- src/app/api/auth/{login,register,logout} تدعم Supabase (login=signInWithPassword، register=signUp مع
  user_metadata.km_role دون أي كتابة في user_profiles، logout=signOut).
- src/middleware.ts + src/app/(app)/layout.tsx يفرضان الفصل: المتعلّم ممنوع من النظام الإداري.
- src/lib/kmUser.ts:ensureKmUser يطابق المستخدم في جدول User بالمنصّة قبل أي كتابة محتوى.
- التخزين: src/app/api/videos/upload يولّد رابط رفع موقّعاً (دلو academy-videos)؛ الواجهة ترفع مباشرةً.
- التضمين: مزوّد gemini في src/lib/ai/embeddings.ts (text-embedding-004, 768).
- مزامنة المحتوى: scripts/sync-from-supabase.ts يستورد operations_admin_letters → Document. سكربت npm: sync:content.
- فصل الإعداد: NEXT_PUBLIC_SUPABASE_* (مصادقة/قراءة من المشروع الحالي) منفصل عن DATABASE_URL (بيانات المنصّة المعزولة).

## لماذا هذا الحلّ أفضل وأدقّ (خارج البرومبت)

- **عزل تامّ للبيانات:** بيانات المنصّة في **قاعدة منفصلة**، فهجرات Prisma لا تستطيع فيزيائياً لمس جداول نظام المركبات — أعلى درجات الأمان ضدّ التخريب.
- **هوية موحّدة بلا تكرار:** الموظفون يدخلون بحساباتهم الحالية في Supabase؛ الكود يفصل إعداد المصادقة (المشروع الحالي) عن إعداد البيانات (قاعدة المنصّة) — لذا الجمع بين «هوية مشتركة» و«بيانات معزولة» يتحقّق دون تعارض.
- **نظامك التشغيلي للقراءة فقط:** المنصّة لا تكتب في `user_profiles` ولا في أي جدول لديك؛ دور المتعلّم يُحفظ في `user_metadata` وفي جدول `User` الخاص بالمنصّة.
- **زر «النظام» مرن:** يوجّه إلى رابط نظام المركبات عبر `NEXT_PUBLIC_SYSTEM_URL`، أو إلى دخول النظام داخل المنصّة إن تركته فارغاً.
- **بديل واضح:** إن أردت مشروعاً واحداً، الاستراتيجية 2 (schema باسم km) متاحة وموثّقة، مع نفس ضوابط الأمان.

> بخصوص «المشكلة في نظام المنصّة»: إن كانت رسالة خطأ محدّدة (شاشة بيضاء، خطأ بناء، فشل دخول…)، أرسل لي نصّها أو لقطة منها وأحلّها فوراً. التحديثات أعلاه تضبط اسم المنصّة والزرّين وتشدّد العزل والأمان في آلية الربط.
